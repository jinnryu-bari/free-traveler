---
description: Orchestrate one Wave — pick the next READY Task in Depends On order, gate it with prepare-task, implement it with implement-task, commit it, repeat until the Wave is DONE or blocked. No auto Branch/PR/Merge.
---

## Inputs

| Name | Required | Meaning |
|---|---|---|
| `WAVE_ID` | yes | The Wave to act on (e.g. `W03`). Always the first/positional argument — every invocation below names one. |
| `--status` | no (mutually exclusive with `--dry-run`/`--resume`) | Read-only. Report `WAVE_ID`'s current status and its Tasks' status. No mutation. |
| `--dry-run` | no (mutually exclusive with `--status`/`--resume`) | Simulate `WAVE_ID`'s whole execution order and run `/prepare-task` (gate only) for each Task in sequence. Never calls `/implement-task`, never commits, never writes `TASKS/WAVE_STATE.json`. |
| `--resume` | no (mutually exclusive with `--status`/`--dry-run`) | Re-enter `WAVE_ID` starting from its first Task that is not `"done"` (`"pending"` or any `blocked_*` value), even if `WAVE_ID` itself is currently recorded `blocked_*`. Otherwise runs the same Task loop as the default mode. |
| (no flag) | — | Default. Pick the next READY Task in `WAVE_ID` and `/prepare-task` + `/implement-task` it, one Task at a time, looping until the Wave is `done`, `waiting_for_preview`, or `blocked_*`. |

If more than one of `--status`/`--dry-run`/`--resume` is given in one invocation, stop and report the invocation as invalid — pick exactly one.

## Supported invocations

| Command | Behavior |
|---|---|
| `/run-wave W03` | Default. Run Wave `W03` — process its Tasks one at a time until DONE, blocked, or a Preview Checkpoint is hit. Refuses to start if `W03` (or an earlier Wave) is not eligible — see Rule 1 and Step 1. |
| `/run-wave W03 --status` | Read-only. Report `W03`'s Wave-level status and a per-Task breakdown. No mutation. |
| `/run-wave W03 --dry-run` | Simulate `W03`'s whole execution order and run `/prepare-task` (gate only) for each Task in sequence. Never calls `/implement-task`, never commits, never writes `TASKS/WAVE_STATE.json`. |
| `/run-wave W03 --resume` | Re-enter `W03` from its first `"pending"` or `blocked_*` Task (including when `W03` itself is currently `blocked_*`), then continue the normal Task loop. If `W03` is `"waiting_for_preview"` instead, this is what asks the human to confirm the Preview (see Rule 5 / Step 6). |

## Canonical files

| File | Role | Mutated by this command? |
|---|---|---|
| `TASKS/WAVE_PLAN.md` | Static: which Task IDs belong to which Wave, and which Waves require a human Preview Checkpoint before the next Wave may start. Also defines Wave *order* (top to bottom) — used by Rule 1. | No — read-only input. |
| `TASKS/WAVE_STATE.json` | Dynamic: current Status of every Task and every Wave. This is what makes `--resume` and `--status` possible across sessions. | Yes, by default/`--resume` runs only (never by `--status` or `--dry-run`). |
| `TASKS/00_TASK_LIST.md` | Task metadata (Depends On, Expected Files, Category, AC). | No. |

Both `TASKS/WAVE_PLAN.md` and `TASKS/WAVE_STATE.json` are generated by `scripts/build_waves.py`, not hand-written — if either is missing or `TASKS/TASK_MANIFEST.csv` has changed since they were generated, run `python scripts/build_waves.py` first (a separate, explicit step, not something this command invents on the fly) and re-read its output before continuing.

**`TASKS/WAVE_PLAN.md` expected shape**:

```markdown
## Wave 목록
| Wave ID | Preview Checkpoint | 설명 |
|---|---|---|
| W01 | yes | ... |

## Task 배정
| Wave ID | Task ID |
|---|---|
| W01 | PAGE-SCR001 |
| W01 | C-SCR001-HERO-SEARCH |
```

**`TASKS/WAVE_STATE.json` expected shape** (this command updates it in place — a JSON document, not a Markdown table; `scripts/build_waves.py` writes the initial version with every Wave at `status: "pending"`):

```json
{
  "schema_version": "traveler-wave-state-v1",
  "generated_at": "2026-09-16T12:27:01Z",
  "waves": [
    {
      "wave_id": "W01",
      "title": "...",
      "task_ids": ["PAGE-SCR001", "C-SCR001-HERO-SEARCH"],
      "status": "in_progress",
      "checkpoint_required": true,
      "checkpoint_result": null
    }
  ]
}
```

`waves[].status` (Wave-level) values: `pending`, `in_progress`, `waiting_for_preview`, `done`, or a `blocked_*` value (`blocked_dirty_tree`/`blocked_input`/`blocked_dependency`/`blocked_scope`) inherited from whichever Task got stuck (Rule 2). There is no separate Task-level status array in the JSON schema `scripts/build_waves.py` produces — this command tracks per-Task progress **within a Wave** by adding a `tasks` object to that Wave's entry the first time it starts working the Wave (keyed by Task ID, each value one of `pending`, `ready` (computed, not stored — all Depends On are `done`), `blocked_input`/`blocked_dependency`/`blocked_dirty_tree`/`blocked_scope` (from `/prepare-task`), `in_progress`, `done`, optionally with a `commit` and `updated` field once `done`). Never rewrite `waves[].task_ids` or `wave_id`/`title` — those belong to `scripts/build_waves.py`; this command only ever adds/updates `status`, `checkpoint_result`, and the per-Wave `tasks` map.

`checkpoint_required`/`checkpoint_result` are already present from generation (`checkpoint_result` starts `null`); this command only ever writes a value into `checkpoint_result` when a human confirms a Preview (see `--resume` on a `waiting_for_preview` Wave), never clears `checkpoint_required` itself. Rule 4 below also has this command independently re-derive whether a Wave *should* require a Checkpoint, as a defensive cross-check against stale generated data.

`docs/DECISION_LOG.md` DEC-010/DEC-011 record that Wave splitting is `scripts/build_waves.py`'s job — don't re-litigate the split here.

## Rules (apply to every invocation of this command)

1. **이전 Wave가 completed가 아니면 시작하지 않는다.** Before doing anything else for a real run (default or `--resume`), find `WAVE_ID`'s position in `TASKS/WAVE_PLAN.md`'s Wave 목록 order. Every Wave listed *before* it must show `status: "done"` in `TASKS/WAVE_STATE.json`. If any earlier Wave is not `"done"` → stop immediately, do not touch any Task or file, and report exactly which earlier Wave(s) are not done yet. (`--status` and `--dry-run` still report this as informational — a `--dry-run` shows it as the first point a real run would refuse to start — but do not themselves refuse to display it.)
2. **Task 하나가 blocked면 Wave를 blocked로 기록하고 멈춘다.** Whenever a Task's gate (`/prepare-task`) or implementation (`/implement-task`) ends in a `BLOCKED_*`/unresolved state, this command writes that Task's own `blocked_*` value into `WAVE_ID.tasks[<task>]` **and** copies the same `blocked_*` value onto `WAVE_ID.status` itself (Wave-level), then stops the run. A Wave never stays `"in_progress"` while one of its Tasks is blocked.
3. **Task마다 지정된 최소 검증을 실행한다.** Every Task run through this command goes through `/implement-task`'s own Step 3 (lint/build/type-check, plus any Unit/Integration Test that covers the Task) unconditionally — never skip these to save time, and never mark a Task `"done"` if any of them failed.
4. **Page Owner가 있는 Wave는 Browser Checkpoint를 요구한다.** Independently of what `checkpoint_required` already says in `TASKS/WAVE_STATE.json`, if any Task in `WAVE_ID.task_ids` has Category `PAGE_OWNER`, treat this Wave as requiring a human Preview Checkpoint before the next Wave may start — even if the stored `checkpoint_required` were `false` (stale generation), report the mismatch and follow the safer path (require the Checkpoint).
5. **사람의 확인 전에는 다음 Wave를 자동 실행하지 않는다.** Once every Task in `WAVE_ID` is `"done"` and Rule 4 applies, set `WAVE_ID.status` to `"waiting_for_preview"` and stop — never start the next Wave ID in the same or a later invocation without an explicit human confirmation (see Step 6).
6. **자동 Commit·Push·PR·Merge를 하지 않는다** — except the one, narrowly-scoped exception this command has always had: after a single Task passes `/implement-task`, this command stages and commits **only that Task's own Expected Files** (Step 5) so that the next Task's `/prepare-task` dirty-tree check doesn't immediately fail on the previous Task's own uncommitted output. That single-Task commit is the *only* git-mutating action this command ever performs. No branch is ever created, no `git push` ever runs, no Pull Request is ever opened, and no merge is ever performed — automatically or on request — by any invocation of `/run-wave` (`CLAUDE.md` rules 20–21, `docs/DECISION_LOG.md` DEC-012).

## `/run-wave WAVE_ID` (default) — full procedure

### Step 1 — Read `WAVE_PLAN.md` and `WAVE_STATE.json`, apply Rule 1

- If `TASKS/WAVE_PLAN.md` or `TASKS/WAVE_STATE.json` doesn't exist, or `WAVE_ID` isn't listed → stop, report the missing input, tell the user to run `python scripts/build_waves.py` first. Do not initialize either file yourself — generation is that script's job, not this command's.
- Find `WAVE_ID`'s entry in `WAVE_STATE.json`'s `waves` array.
- Apply **Rule 1**: confirm every Wave before `WAVE_ID` in `WAVE_PLAN.md`'s order is `"done"`. If not → stop, report which earlier Wave(s) block it.
- If `WAVE_ID`'s own `status` is already `"done"` → stop, report "already complete", do nothing else.
- If its `status` is `"waiting_for_preview"` → stop, report that a human Preview confirmation is required (`/run-wave WAVE_ID --resume` handles that — see Step 6) — do not silently clear the checkpoint here.
- If its `status` is any `blocked_*` value → stop, report the Wave is blocked and that `--resume` (not the default invocation) is required to retry it.
- If `WAVE_ID` has no `tasks` map yet in `WAVE_STATE.json` (first time this Wave is being worked), treat every Task ID in its `task_ids` as implicitly `"pending"` until Step 3 first sets one.

### Step 2 — Pick the next READY Task, in Depends On order

- Take `WAVE_ID`'s `task_ids` from `WAVE_STATE.json` (same list `WAVE_PLAN.md`'s Task 배정 has it under). Topologically order them by `TASKS/00_TASK_LIST.md`'s Depends On graph (a Task may depend on a Task from an earlier, already-`"done"` Wave — that's fine, treat it as satisfied if that Wave's entry in `WAVE_STATE.json` shows it `"done"` in its `tasks` map).
- Walk the ordered list; the first Task that is not `"done"` in `WAVE_ID.tasks` and whose every Depends On shows `"done"` (in whichever Wave owns that dependency) is the one to run next.
- If every Task in `WAVE_ID` is already `"done"` → skip to Step 6 (Wave complete).
- If no Task qualifies (something not `"done"` exists, but none has all dependencies satisfied) → stop, report exactly which Task(s) are stuck and on which unmet dependency, set that Task's entry in `WAVE_ID.tasks` to `"blocked_dependency"` **and** `WAVE_ID.status` to `"blocked_dependency"` in `WAVE_STATE.json` (Rule 2), and end the run. **Do not skip ahead to a different, later Task out of order** — `CLAUDE.md` rule 7 and `docs/DECISION_LOG.md` DEC-011 require strict single-Task, Depends-On-ordered, single-Agent execution.

### Step 3 — Gate it with `/prepare-task`

Run `/prepare-task` with `WAVE_ID`, `TASK_ID=<selected>`.

- Not `READY_TO_IMPLEMENT` → record that exact `BLOCKED_*` status (lowercased, e.g. `"blocked_dirty_tree"`) for the Task in `WAVE_ID.tasks`, copy the same value onto `WAVE_ID.status` (Rule 2), stop the whole run here (same "don't skip ahead" rule as Step 2), and report.
- `READY_TO_IMPLEMENT` → set the Task's entry in `WAVE_ID.tasks` to `"in_progress"` in `WAVE_STATE.json`, continue.

### Step 4 — Implement it with `/implement-task`

Run `/implement-task` for the same `WAVE_ID`/`TASK_ID`. Let it do Steps 0–6 of its own procedure (re-gate, implement inside Expected Files, run AC/tests/lint/build — Rule 3 — Page-Owner-or-E2E-only Playwright, diff check, report).

- If it reports a verification failure it couldn't self-resolve (lint/build/Unit Test/Playwright failed and the fix would go outside Expected Files) → leave the Task `"in_progress"` in `WAVE_STATE.json`, set `WAVE_ID.status` to `"blocked_verification"` (Rule 2), stop the run, report the failure. Do not mark it `"done"` and do not move to the next Task.

### Step 5 — On PASS, commit and mark DONE

Per **Rule 6**, this is the one place `/run-wave` mutates git — necessary because the next Task's `/prepare-task` dirty-tree check would otherwise immediately fail on this Task's own uncommitted changes, which would make sequential Wave execution impossible.

- Stage **only** this Task's Expected Files (`git add <expected files>` — never `git add -A`/`git add .`) and commit, with the Task ID and a one-line summary in the message.
- Update `TASKS/WAVE_STATE.json`: this Task's entry in `WAVE_ID.tasks` → `"done"`, with `commit` (the SHA) and `updated` (the date) fields recorded alongside it.
- No branch, push, PR, or merge — ever (Rule 6).

### Step 6 — Loop or finish

- Go back to Step 2 to pick the next READY Task in `WAVE_ID`.
- When every Task in `WAVE_ID` is `"done"`:
  - **Rule 4**: if any Task in `WAVE_ID` has Category `PAGE_OWNER` (independently re-derived, not just trusting the stored `checkpoint_required`) → set `WAVE_ID.status` to `"waiting_for_preview"` in `WAVE_STATE.json`, stop, and tell the user a human needs to review the Preview before the next Wave starts (`CLAUDE.md` rule 22, Rule 5 above).
  - Otherwise → set `WAVE_ID.status` to `"done"`, stop, and report the Wave complete.
- Either way, end with the **종료 보고** (Step 7 below).

### Step 7 — 종료 보고 (every real run, whatever the outcome)

Report exactly these five items, every time a default or `--resume` run ends (whether it finished the Wave, hit a Checkpoint, or stopped on a blocker):

- **완료 Task** — every Task ID newly marked `"done"` during this invocation (empty list if none).
- **변경 파일** — the union of Expected Files committed across those Tasks this run, each tagged create/extend.
- **통과한 검사** — which lint/build/type-check/Unit/Integration/Playwright checks ran and passed for those Tasks (per Rule 3); note any that were correctly skipped (e.g. Playwright for a non-`PAGE_OWNER`/`E2E_TEST` Task).
- **남은 수동 Browser 확인** — whether `WAVE_ID` is now `"waiting_for_preview"` (Rule 4/5) and, if so, exactly what a human needs to open and confirm; otherwise state plainly that no Preview confirmation is currently pending for this Wave.
- **다음에 입력할 명령** — the exact next command the user should type: `/run-wave <next Wave ID>` if this Wave is `"done"` and not gated; `/run-wave WAVE_ID --resume` (after a human confirms the Preview) if `"waiting_for_preview"`; `/run-wave WAVE_ID --resume` (after fixing the blocker) if a `blocked_*` status was hit; or nothing further if the Wave isn't finished yet but stopped mid-Task for another reason.

## `/run-wave WAVE_ID --status`

Read `TASKS/WAVE_PLAN.md` and `TASKS/WAVE_STATE.json` (read-only, no writes). Report `WAVE_ID`'s Wave-level `status`, whether it requires a Preview Checkpoint (Rule 4, cross-checked against its Tasks' Categories), and a per-Task breakdown (`done`/`in_progress`/`blocked_*`/`pending`, from that Wave's `tasks` map — Tasks with no entry yet count as `pending`). Also state, per Rule 1, whether every earlier Wave in `WAVE_PLAN.md`'s order is `"done"` (i.e. whether `WAVE_ID` is even eligible to start/continue).

## `/run-wave WAVE_ID --resume`

- If `WAVE_ID.status` is `"waiting_for_preview"` → **ask the user directly** whether they've reviewed the Preview for this Wave. Only on an explicit yes, set `WAVE_ID.status` to `"done"` and `checkpoint_result` to a short confirmation record (e.g. `{"confirmed_by": "user", "confirmed_at": "<ISO date>"}`) in `WAVE_STATE.json`, and tell the user which Wave to run next (Rule 5) — do not auto-start it in the same invocation. On no/unclear, stop and wait.
- If `WAVE_ID.status` is `"in_progress"` or any `blocked_*` value → re-apply Rule 1, then resume exactly the default procedure from Step 2, starting from `WAVE_ID`'s first Task that is not `"done"` (`"pending"` or `blocked_*`) — do not re-run already-`"done"` Tasks.
- If `WAVE_ID.status` is `"pending"` (never started) → behave exactly like the default invocation (there is nothing to resume from yet).
- If `WAVE_ID.status` is already `"done"` → stop, report "already complete", do nothing else.

## `/run-wave WAVE_ID --dry-run`

Same as the default invocation's Steps 1–2, but:

- Walk the **entire** ordered Task list for `WAVE_ID`, not just the next one.
- For each Task in order, run `/prepare-task` treating every earlier Task in this simulated walk as if it were already `"done"` (even though nothing has actually run) — this projects the whole Wave's sequence.
- Never call `/implement-task`. Never commit. Never write `TASKS/WAVE_STATE.json`.
- Report the full projected sequence — each Task with its Expected Files, the minimum verification it would run (Rule 3), and whether a Preview Checkpoint would be required at the end (Rule 4) — and the first point (if any) where a real run would stop, with the reason (including a Rule 1 violation, if `WAVE_ID` isn't even eligible to start yet) — so the user can fix `WAVE_PLAN.md`/`TASKS/00_TASK_LIST.md`/environment issues before spending a real `/run-wave WAVE_ID` run on it.

## Absolute exclusions (all invocation forms)

No invocation of `/run-wave` ever creates a git branch, opens a Pull Request, or performs a merge — automatically or on request (Rule 6). Those remain fully manual, per `CLAUDE.md` rules 20–22 and `docs/DECISION_LOG.md` DEC-012. The only git-mutating action anywhere in this command is the single-Task commit in the default/`--resume` procedure's Step 5.
