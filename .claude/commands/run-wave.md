---
description: Orchestrate one Wave — pick the next READY Task in Depends On order, gate it with prepare-task, implement it with implement-task, commit it, repeat until the Wave is DONE or blocked. No auto Branch/PR/Merge.
---

## Supported invocations

| Command | Behavior |
|---|---|
| `/run-wave W03` | Run Wave `W03` — process its Tasks one at a time until DONE, blocked, or a Preview Checkpoint is hit. |
| `/run-wave status` | Read-only. Report every Wave's status and every Task's status. No mutation. |
| `/run-wave resume` | Continue whichever Wave was left `IN_PROGRESS`. If the most recent Wave is `WAITING_FOR_PREVIEW`, ask the user to confirm the Preview before doing anything else. |
| `/run-wave dry-run W03` | Simulate `W03`'s whole execution order and run `/prepare-task` (gate only) for each Task in sequence. Never calls `/implement-task`, never commits, never writes `TASKS/WAVE_STATE.json`. |

## Canonical files

| File | Role | Mutated by this command? |
|---|---|---|
| `TASKS/WAVE_PLAN.md` | Static: which Task IDs belong to which Wave, and which Waves require a human Preview Checkpoint before the next Wave may start. | No — read-only input. |
| `TASKS/WAVE_STATE.json` | Dynamic: current Status of every Task and every Wave. This is what makes `resume` and `status` possible across sessions. | Yes, by `/run-wave W03` only (never by `status` or `dry-run`). |
| `TASKS/00_TASK_LIST.md` | Task metadata (Depends On, Expected Files, Category, AC). | No. |

Both `TASKS/WAVE_PLAN.md` and `TASKS/WAVE_STATE.json` are generated by `scripts/build_waves.py`, not hand-written — if either is missing or `TASKS/TASK_MANIFEST.csv` has changed since they were generated, run `python scripts/build_waves.py` first (a separate, explicit step, not something this command invents on the fly) and re-read its output before continuing.

**`TASKS/WAVE_PLAN.md` expected shape**:

```markdown
## Wave 목록
| Wave ID | Preview Checkpoint | 설명 |
|---|---|---|
| W01 | yes | ... |

## Task 배정
| Wave ID | Task ID |
|---|---|
| W01 | PAGE-SCR001 |
| W01 | C-SCR001-HERO-SEARCH |
```

**`TASKS/WAVE_STATE.json` expected shape** (this command updates it in place — a JSON document, not a Markdown table; `scripts/build_waves.py` writes the initial version with every Wave at `status: "pending"`):

```json
{
  "schema_version": "traveler-wave-state-v1",
  "generated_at": "2026-09-16T12:27:01Z",
  "waves": [
    {
      "wave_id": "W01",
      "title": "...",
      "task_ids": ["PAGE-SCR001", "C-SCR001-HERO-SEARCH"],
      "status": "in_progress",
      "checkpoint_required": true,
      "checkpoint_result": null
    }
  ]
}
```

`waves[].status` (Wave-level) values: `pending`, `in_progress`, `waiting_for_preview`, `done`, or a `blocked_*` value inherited from its stuck Task. There is no separate Task-level status array in the JSON schema `scripts/build_waves.py` produces — this command tracks per-Task progress **within a Wave** by adding a `tasks` object to that Wave's entry the first time it starts working the Wave (keyed by Task ID, each value one of `pending`, `ready` (computed, not stored — all Depends On are `done`), `blocked_input`/`blocked_dependency`/`blocked_dirty_tree`/`blocked_scope` (from `/prepare-task`), `in_progress`, `done`, optionally with a `commit` and `updated` field once `done`). Never rewrite `waves[].task_ids` or `wave_id`/`title` — those belong to `scripts/build_waves.py`; this command only ever adds/updates `status`, `checkpoint_result`, and the per-Wave `tasks` map.

`checkpoint_required`/`checkpoint_result` are already present from generation (`checkpoint_result` starts `null`); this command only ever writes a value into `checkpoint_result` when a human confirms a Preview (see `/run-wave resume`), never clears `checkpoint_required` itself.

`docs/DECISION_LOG.md` DEC-010/DEC-011 record that Wave splitting is `scripts/build_waves.py`'s job — don't re-litigate the split here.

## `/run-wave W03` — full procedure

### Step 1 — Read `WAVE_PLAN.md` and `WAVE_STATE.json`

- If `TASKS/WAVE_PLAN.md` or `TASKS/WAVE_STATE.json` doesn't exist, or `W03` isn't listed → stop, report the missing input, tell the user to run `python scripts/build_waves.py` first. Do not initialize either file yourself — generation is that script's job, not this command's.
- Find `W03`'s entry in `WAVE_STATE.json`'s `waves` array.
- If its `status` is already `"done"` → stop, report "already complete", do nothing else.
- If its `status` is `"waiting_for_preview"` → stop, report that a human Preview confirmation is required (see `/run-wave resume`'s handling below) — do not silently clear the checkpoint from `/run-wave W03` itself.
- If `W03` has no `tasks` map yet in `WAVE_STATE.json` (first time this Wave is being worked), treat every Task ID in its `task_ids` as implicitly `"pending"` until Step 3 first sets one.

### Step 2 — Pick the next READY Task, in Depends On order

- Take `W03`'s `task_ids` from `WAVE_STATE.json` (same list `WAVE_PLAN.md`'s Task 배정 has it under). Topologically order them by `TASKS/00_TASK_LIST.md`'s Depends On graph (a Task may depend on a Task from an earlier, already-`"done"` Wave — that's fine, treat it as satisfied if that Wave's entry in `WAVE_STATE.json` shows it `"done"` in its `tasks` map).
- Walk the ordered list; the first Task that is not `"done"` in `W03.tasks` and whose every Depends On shows `"done"` (in whichever Wave owns that dependency) is the one to run next.
- If every Task in `W03` is already `"done"` → skip to Step 6 (Wave complete).
- If no Task qualifies (something not `"done"` exists, but none has all dependencies satisfied) → stop, report exactly which Task(s) are stuck and on which unmet dependency, set that Task's entry in `W03.tasks` to `"blocked_dependency"` in `WAVE_STATE.json`, and end the run. **Do not skip ahead to a different, later Task out of order** — `CLAUDE.md` rule 7 and `docs/DECISION_LOG.md` DEC-011 require strict single-Task, Depends-On-ordered, single-Agent execution.

### Step 3 — Gate it with `/prepare-task`

Run `/prepare-task` with `WAVE_ID=W03`, `TASK_ID=<selected>`.

- Not `READY_TO_IMPLEMENT` → record that exact `BLOCKED_*` status (lowercased, e.g. `"blocked_dirty_tree"`) for the Task in `W03.tasks` in `WAVE_STATE.json`, stop the whole run here (same "don't skip ahead" rule as Step 2), and report.
- `READY_TO_IMPLEMENT` → set the Task's entry in `W03.tasks` to `"in_progress"` in `WAVE_STATE.json`, continue.

### Step 4 — Implement it with `/implement-task`

Run `/implement-task` for the same `WAVE_ID`/`TASK_ID`. Let it do Steps 0–6 of its own procedure (re-gate, implement inside Expected Files, run AC/tests/lint/build, Page-Owner-or-E2E-only Playwright, diff check, report).

- If it reports a verification failure it couldn't self-resolve (lint/build/Unit Test/Playwright failed and the fix would go outside Expected Files) → leave the Task `"in_progress"` in `WAVE_STATE.json`, stop the run, report the failure. Do not mark it `"done"` and do not move to the next Task.

### Step 5 — On PASS, commit and mark DONE

This is the one place `run-wave` commits automatically — necessary because the next Task's `/prepare-task` dirty-tree check would otherwise immediately fail on this Task's own uncommitted changes, which would make sequential Wave execution impossible.

- Stage **only** this Task's Expected Files (`git add <expected files>` — never `git add -A`/`git add .`) and commit, with the Task ID and a one-line summary in the message.
- Update `TASKS/WAVE_STATE.json`: this Task's entry in `W03.tasks` → `"done"`, with `commit` (the SHA) and `updated` (the date) fields recorded alongside it.
- **No branch is created, no push happens, no PR is opened, no merge is performed** — this command never does any of those three, with or without a user request (that restriction is absolute here, unlike `/implement-task`'s commit-only opt-in).

### Step 6 — Loop or finish

- Go back to Step 2 to pick the next READY Task in `W03`.
- When every Task in `W03` is `"done"`:
  - If `W03`'s `checkpoint_required` is `true` → set `W03.status` to `"waiting_for_preview"` in `WAVE_STATE.json`, stop, and tell the user a human needs to review the Preview before the next Wave starts (`CLAUDE.md` rule 22).
  - Otherwise → set `W03.status` to `"done"`, stop, and report the Wave complete.

## `/run-wave status`

Read `TASKS/WAVE_PLAN.md` and `TASKS/WAVE_STATE.json` (read-only, no writes). For every Wave, report its `status` and a per-Task breakdown (counts of `done`/`in_progress`/`blocked_*`/`pending`, from that Wave's `tasks` map — Tasks with no entry yet count as `pending`). Call out clearly which Wave (if any) is `in_progress` or `waiting_for_preview`, since that's what `resume` will act on.

## `/run-wave resume`

- Find the Wave with `status: "in_progress"` in `TASKS/WAVE_STATE.json`.
  - None found, but one is `"waiting_for_preview"` → **ask the user directly** whether they've reviewed the Preview for that Wave. Only on an explicit yes, set that Wave's `status` to `"done"` and `checkpoint_result` to a short confirmation record (e.g. `{"confirmed_by": "user", "confirmed_at": "<ISO date>"}`) in `WAVE_STATE.json`, and tell the user which Wave to run next (`/run-wave W0<n+1>`) — do not auto-start it in the same invocation. On no/unclear, stop and wait.
  - None found at all (every Wave `"pending"`, `"done"`, or none defined) → report that, and do nothing else.
- Found an `"in_progress"` Wave → resume exactly `/run-wave <that Wave ID>`'s procedure from Step 2 (do not re-run already-`"done"` Tasks).

## `/run-wave dry-run W03`

Same as `/run-wave W03` Steps 1–2, but:

- Walk the **entire** ordered Task list for `W03`, not just the next one.
- For each Task in order, run `/prepare-task` treating every earlier Task in this simulated walk as if it were already `"done"` (even though nothing has actually run) — this projects the whole Wave's sequence.
- Never call `/implement-task`. Never commit. Never write `TASKS/WAVE_STATE.json`.
- Report the full projected sequence and the first point (if any) where a real run would stop, with the reason — so the user can fix `WAVE_PLAN.md`/`TASKS/00_TASK_LIST.md`/environment issues before spending a real `/run-wave W03` run on it.

## Absolute exclusions (all four sub-commands)

No invocation of `/run-wave` ever creates a git branch, opens a Pull Request, or performs a merge — automatically or on request. Those remain fully manual, per `CLAUDE.md` rules 20–22 and `docs/DECISION_LOG.md` DEC-012. The only git-mutating action anywhere in this command is the single-Task commit in `/run-wave W03` Step 5.
