---
description: Read-only readiness gate for one Task before implementation — checks Working Tree, Wave membership, Depends On, Expected Files, doc refs, env vars, secret risk, and EXCLUDED scope; never edits code
---

## Inputs

| Name | Required | Meaning |
|---|---|---|
| `WAVE_ID` | yes | The Wave this Task is being prepared for (e.g. `W01`). See `docs/DECISION_LOG.md` DEC-010/DEC-011 — Wave is the execution unit, a single Agent works its Tasks sequentially. |
| `TASK_ID` | yes | The Task ID from `TASKS/00_TASK_LIST.md` §2 (e.g. `PAGE-SCR001`, `C-SCR003-FLIGHT-FORM`). |
| 선택된 상세 Task 파일 | yes | Path to the detail file for `TASK_ID`, normally `TASKS/TASK-<TASK_ID>.md`. If the caller passes a different path, treat any mismatch with `TASK_ID` as a failure of Check 4 below. |

## What this command is and is not

**This is a read-only gate.** It runs before `CLAUDE.md`'s Task 완료 순서 step "구현" begins. It never:
- edits `src/**`, `supabase/**`, `TASKS/**`, or `docs/**`,
- runs a mutating git command (`add`, `commit`, `checkout`, `reset`, `stash`, `clean`, `merge`, `branch -D`, etc.) — only `git status`/`git log` (read-only) are allowed,
- prints the value of any environment variable or secret (only whether a variable **name** is defined, never its value).

If any step above would require a mutation to complete a check, stop and report the check as failed/undetermined instead of performing the mutation.

## Step 0 — Resolve inputs

1. Read `TASKS/00_TASK_LIST.md` fresh. Find the §2 row whose Task ID equals `TASK_ID`.
   - Not found in §2, but found in the §4 NON_IMPLEMENTATION (EXCLUDED) table → this is not a Task at all. Skip straight to the final status: **`BLOCKED_SCOPE`** ("`TASK_ID`는 EXCLUDED 요구사항이며 구현 대상 Task가 아니다").
   - Not found in either §2 or §4 → **`BLOCKED_INPUT`** ("`TASK_ID`가 `TASKS/00_TASK_LIST.md`에 존재하지 않는다").
2. Read the detail file at the given path (default `TASKS/TASK-<TASK_ID>.md`). If it doesn't exist, or its `# <TASK-ID> —` header doesn't match `TASK_ID` → **`BLOCKED_INPUT`**.
3. If both resolve, continue to the 8 checks below. Run all 8 regardless of early failures — report every check's result, then pick one final status per Step 9's priority order.

## The 8 checks

### 1. Working Tree 상태

Run:

```
git status --short
```

- If output is empty → clean, check passes.
- If output only touches files inside this Task's own **Expected Files** (from §2, `없음` excluded) → not a blocker; note "이전 실행에서 이 Task가 이미 부분적으로 시작된 것으로 보인다" as information, check still passes.
- If output touches any file **outside** this Task's Expected Files (leftover changes from another Task, or unrelated edits) → fails this check, contributes to **`BLOCKED_DIRTY_TREE`**.

### 2. Task가 현재 Wave에 포함되는지

Canonical Wave→Task mapping lives in `TASKS/WAVE_PLAN.md` (static assignment: which Task IDs belong to which Wave — see `.claude/commands/run-wave.md` for its exact shape). Live per-Task/per-Wave progress lives separately in `TASKS/WAVE_STATE.json`, written by `/run-wave`. Both files are generated by `scripts/build_waves.py` from `TASKS/TASK_MANIFEST.csv` — they are not hand-written.

- If `TASKS/WAVE_PLAN.md` does not exist yet → fails this check, contributes to **`BLOCKED_INPUT`** ("Wave Plan 문서가 아직 없어 Wave 소속을 확인할 수 없다 — `python scripts/build_waves.py`를 먼저 실행해야 한다").
- If it exists but `TASK_ID` is not listed under `WAVE_ID` (belongs to a different Wave, or isn't planned into any Wave yet) → fails this check, contributes to **`BLOCKED_SCOPE`** ("`TASK_ID`는 `WAVE_ID`에 속하지 않는다").
- If `TASKS/WAVE_STATE.json` exists and `WAVE_ID`'s entry already shows `status` `"waiting_for_preview"` or `"done"` → fails this check, contributes to **`BLOCKED_SCOPE`** ("`WAVE_ID`는 이미 완료되었거나 Preview 대기 중이다 — 새 Task를 시작할 시점이 아니다").
- Otherwise (listed under `WAVE_ID`, and that Wave is not yet finished) → check passes.

### 3. Depends On 완료 여부

Read `TASK_ID`'s Depends On list (§2 cell, `;`-separated). For each dependency id:

- Look up its §2 row's Expected Files.
- **File-bearing dependency** (Expected Files ≠ `없음`): complete only if every listed file (a) exists on disk, and (b) has at least one commit touching it (`git log --oneline -- <file>` is non-empty) — existing only as an *uncommitted* working-tree change does not count as complete.
- **File-less dependency** (`MANUAL_CHECK`/`RELEASE_CHECK`, Expected Files = `없음`): cannot be verified from the file tree. Treat as complete only if `TASKS/WAVE_STATE.json` shows that dependency's Task status as `"done"` in its owning Wave's `tasks` map, or `git log --all --grep="<DEP_ID>"` finds a commit that references it. Otherwise mark "확인 불가 — 수동 확인 필요" and treat as **not** complete (conservative default).
- **Any dependency, as a cross-check**: if `TASKS/WAVE_STATE.json` exists and shows the dependency's Task status as something other than `"done"` (e.g. still `"pending"`, `"in_progress"`, or a `"blocked_*"` value, or simply absent from its Wave's `tasks` map), treat it as not complete even if the file-existence heuristic above looked satisfied — `WAVE_STATE.json` is the more authoritative signal once it exists.
- If any dependency is not complete → fails this check, contributes to **`BLOCKED_DEPENDENCY`**, listing exactly which dependency id(s) are incomplete and why.

### 4. Expected Files

- Confirm the detail file's **Expected Files** section lists exactly the same files as the §2 row's Expected Files cell. Any mismatch → fails this check, **`BLOCKED_INPUT`** ("Task List와 상세 파일의 Expected Files가 다르다").
- For each file, classify "create" (doesn't exist yet) vs "extend" (exists already) — report both lists, this is informational for the implementer, not a blocker by itself.
- Scan `TASKS/00_TASK_LIST.md` §2 for any *other* Task whose Expected Files overlaps with `TASK_ID`'s Expected Files (an ownership collision that shouldn't exist). If found → fails this check, **`BLOCKED_INPUT`** ("Expected Files가 다른 Task(`<other id>`)와 겹친다 — Task List 자체의 결함").

### 5. SRS·Scope·Design·Screen Ref

- Expand the detail file's **Requirement Ref** into individual `REQ-FUNC-*`/`REQ-NF-*` ids (same `~`-range/comma-chain rule as `scripts/audit_tasks.py`). Every id must appear somewhere in `docs/PROJECT_SCOPE.md`. (Whether it's IMPLEMENT or EXCLUDED is Check 8's job — here we only confirm the id itself resolves and isn't a typo.)
- The **Screen** field, if `SCR-00N`, must exist in `design-reference/SCREEN_ROUTE_CONTRACT.json`.
- The **Design Ref** section's cited `§N` section numbers must actually exist in `design-reference/D-001/DESIGN.md` and/or `design-reference/UI_CONTRACT.md` (grep for the heading).
- If anything above doesn't resolve → fails this check, contributes to **`BLOCKED_INPUT`**.

### 6. 필요한 환경변수 이름

Determine which env vars this Task needs, per `docs/ARCHITECTURE.md` §9/§15.2:

- Category `DB` or `API`, or Depends On includes any `DB-*`/`API-*` task, or Security/Privacy AC mentions Supabase/RLS/Auth → needs `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`; server-side-only Tasks (`DB-*`, `API-ADMIN-*`, `DB-SEED-BASE`) additionally need `SUPABASE_SERVICE_ROLE_KEY`.
- Otherwise: no env vars needed — check passes trivially.

If env vars are needed: check whether `.env.local` exists and defines each required **name** (`grep -oE '^[A-Z0-9_]+='` on the file — read key names only, never echo a value). Missing file or missing name(s) → fails this check, contributes to **`BLOCKED_INPUT`**, listing exactly which variable **names** (never values) are missing.

### 7. Secret 하드코딩 위험

Two sub-checks, either one failing fails this whole check:

- **Boundary contradiction:** if this Task is a Client Component (any `COMPONENT` category Task whose UI is interactive per `design-reference/UI_CONTRACT.md`/`docs/ARCHITECTURE.md` §3) and its Requirement Ref or Context implies it needs `SUPABASE_SERVICE_ROLE_KEY` or another server-only secret → contradiction with `CLAUDE.md` rule 15. Fails this check.
- **Existing hardcoded secret:** for every Expected File that already exists on disk (the "extend" set from Check 4), grep it for secret-shaped literals (`SUPABASE_SERVICE_ROLE_KEY\s*=\s*["'][^"']{10,}`, or a string literal assigned to a variable named like `key`/`secret`/`token` that isn't `process.env.*`). Any match → fails this check.

If both sub-checks are clean, the check passes; still print which secret-handling rules apply to this Task (rule 14/15 from `CLAUDE.md`) as a reminder for the implementer.

A failure here contributes to **`BLOCKED_SCOPE`**.

### 8. EXCLUDED 범위 침범 여부

- None of the ids from Check 5's Requirement Ref expansion may appear in `docs/PROJECT_SCOPE.md`'s EXCLUDED set or `TASKS/00_TASK_LIST.md` §4. Any that do → fails this check, **`BLOCKED_SCOPE`**, naming the offending id(s).
- Soft scan: if the Task's Functional AC / Context text mentions a known EXCLUDED feature area (CMS/콘텐츠 CRUD, 감사 로그, 통합검색, rate limiting, 자동 백업/모니터링 대시보드— see `docs/PROJECT_SCOPE.md` §3, `TASKS/00_TASK_LIST.md` §4) **without** that being explicitly named in the detail file's own **Forbidden** section as something *not* being implemented, flag it as a warning in the report (does not by itself flip the final status, but must be surfaced).

## Step 9 — Decide the final status

Run all 8 checks, then pick exactly one final status by this priority (highest wins):

1. **`BLOCKED_DIRTY_TREE`** — Check 1 failed. Nothing else matters until the tree is clean; report this alone as the primary blocker (still show the other 7 results for context, marked "검사 보류" where a dirty tree makes them unreliable, e.g. Check 4/7's file-state reads).
2. **`BLOCKED_INPUT`** — Check 2 (missing Wave Plan), 4, 5, or 6 failed (and Check 1 passed). Something needed to even evaluate this Task is missing or unresolvable.
3. **`BLOCKED_SCOPE`** — Check 2 (wrong Wave), 7, or 8 failed (and 1/Input-checks passed). The Task is well-formed but doesn't belong here or would cross a boundary.
4. **`BLOCKED_DEPENDENCY`** — Check 3 failed (and nothing above did). The Task itself is ready, but a prerequisite isn't done.
5. **`READY_TO_IMPLEMENT`** — all 8 checks passed.

## Step 10 — Report

Print a checklist (✔/✘ per numbered check, 1–8) with a one-line reason for every ✘, then the single final status on its own line (exactly one of `READY_TO_IMPLEMENT` / `BLOCKED_INPUT` / `BLOCKED_DEPENDENCY` / `BLOCKED_DIRTY_TREE` / `BLOCKED_SCOPE`), then:

- On `READY_TO_IMPLEMENT`: restate Expected Files (create vs extend) and the env vars this Task needs (names only), so the implementer's next step (`CLAUDE.md` Task 완료 순서 "구현") has everything without re-reading the detail file.
- On any `BLOCKED_*`: state exactly what would need to change for the status to flip (e.g. "which commit/PR finishes `C-SCR001-DEST-GRIDS`", "add `NEXT_PUBLIC_SUPABASE_ANON_KEY` to `.env.local`", "create `TASKS/WAVE_PLAN.md`") — never guess or silently work around the blocker.

Never modify any file in this command, regardless of outcome.
