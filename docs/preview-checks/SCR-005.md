## ⚠️ 보안 참고사항 — 확인 및 최소 범위 수정 (2026-09-18 후속 조치)

### 원래 발견 내용

`C-SCR005-ROLE-GATE`(`role-gate.tsx`)를 구현하며 기존 RLS(`supabase/migrations/0002_rls.sql`, W03에 이미 배포됨)를 다시 읽다가 발견했다: `profiles_update_own` 정책은 **행 단위**(`auth.uid() = id`)로만 제한할 뿐 **컬럼 단위** 제한이 없고, `grant select, insert, update on profiles to authenticated`도 전체 컬럼을 열어놨다. 즉 로그인한 일반 사용자가 UI를 거치지 않고 Supabase REST API를 직접 호출해 `PATCH profiles?id=eq.<본인 id>` 요청에 `{"role": "admin"}`을 넣으면 **이론상 자기 자신을 관리자로 승격시킬 수 있었다.**

### 재확인 결과

사용자 지시에 따라 범위를 좁혀 다시 확인했다:
- **UPDATE 경로**: 위에서 설명한 대로 실제로 가능하다(컬럼 권한 제한 없음).
- **INSERT 경로(신규 프로필 생성 시 관리자 role 지정 가능한지)**: `handle_new_user()` 트리거가 `SECURITY DEFINER`로 회원가입 시 자동으로 `profiles` 행을 만들고, 이 트리거는 `role`을 명시적으로 지정하지 않아 컬럼 기본값(`'member'`)이 항상 적용된다. 다만 `profiles_insert_own` 정책과 `grant ... insert ... to authenticated`도 컬럼 제한이 없어, 만약 클라이언트가 (트리거로 이미 생성된 행과 충돌하기 전에) 직접 INSERT를 시도하면 `role` 컬럼도 함께 보낼 수 있는 상태였다 — 실무상 트리거가 먼저 행을 만들어 도달하기 어렵지만, 권한 자체는 막고 있지 않았다.

### 수정 내용 — 새 마이그레이션 `supabase/migrations/0003_profiles_role_lockdown.sql`

기존 `0001_schema.sql`/`0002_rls.sql`은 손대지 않고 새 파일만 추가했다. 범위를 최소로 좁혀 **`profiles` 테이블의 INSERT/UPDATE 컬럼 권한만** 조정한다:

```sql
revoke insert, update on profiles from authenticated;

grant insert (id, nickname, age_range, travel_style, gender)
  on profiles to authenticated;

grant update (nickname, age_range, travel_style, gender, is_adult, adult_verified_at, updated_at)
  on profiles to authenticated;
```

- `role`, `created_at`은 두 GRANT 어디에도 포함하지 않았다 — 일반 사용자는 INSERT/UPDATE 어느 경로로도 자기 `role`을 바꿀 수 없다.
- `nickname`/`age_range`/`travel_style`/`gender`(프로필 Form이 쓰는 컬럼)와 `is_adult`/`adult_verified_at`(성인확인 체크박스가 쓰는 컬럼)은 그대로 UPDATE 가능하다 — `ProfileForm`/성인확인 흐름은 전혀 영향받지 않는다.
- `SELECT`는 건드리지 않았다 — `role` 값 자체는 계속 공개 조회 가능(`RoleGate`가 이를 읽어야 하고, 이 프로젝트 설계상 role 값 노출 자체는 민감정보가 아니다).
- 관리자에게 role을 부여하는 방법은 이 프로젝트 전체 Task 계획에 애초에 없다(운영자가 Supabase SQL Editor에서 직접 `update profiles set role='admin' where id=...`로 처리하는 것이 유일한 경로) — 그래서 `authenticated` 역할 전체에서 role 쓰기를 막아도 정상 기능에 영향이 없다.

### ✅ DB 적용 상태 — 사용자가 실행 완료 (2026-09-18)

사용자가 Supabase 프로젝트 `traveler-dev`의 SQL Editor에서 `supabase/migrations/0003_profiles_role_lockdown.sql`을 실행해 "Success. No rows returned"를 확인했다. **`DB 적용 완료`로 기록한다.**

**단, 이것과 "실제 권한 동작 검증"은 별개다 — 아래에서 명확히 구분한다:**

- **DB 적용(완료)**: SQL이 오류 없이 실행됐다는 것만 의미한다. `revoke`/`grant` 문은 대상 행이 없어도 항상 "Success. No rows returned"를 반환하므로, 이 메시지 자체는 "권한이 실제로 의도대로 좁혀졌는지"까지 보장하지 않는다.
- **권한 동작 검증(미실행)**: 실제로 일반 회원 세션에서 `role` 변경 시도가 거부되는지, 반대로 닉네임 등 정상 프로필 저장은 여전히 되는지는 **이 세션에서 실행하지 못했다.** 이 프로젝트의 seed 계정(`seed-member@example.com` 등, `supabase/seed.sql`)으로 실제 로그인을 시도했으나 **로그인 실패**로 확인됐다. **정정(2026-09-18): 이것만으로 "seed 미적용"을 확정할 수 없다** — `seed.sql`이 `auth.users`에 직접 INSERT하는 방식이라 Supabase Auth(GoTrue)가 로그인에 요구하는 `auth.identities` 레코드가 애초에 만들어지지 않았을 가능성이 있고, 이 세션에는 원인을 구분할 서비스 롤 키가 없다. 자세한 내용과 `seed.sql`을 대신할 계정 준비 절차는 `docs/preview-checks/W13.md`를 참고한다. **따라서 이 보안 수정의 런타임 동작은 여전히 미검증이다(원인 불문).**

**사용자가 가능한 계정으로 직접 확인하고 싶다면(선택):**
1. 아무 계정으로 로그인한 뒤 `/account`에서 닉네임을 바꿔 저장 — 정상 저장되는지(회귀 없는지) 확인.
2. (선택, 기술적 확인) 그 세션의 브라우저 콘솔에서 Supabase 클라이언트로 `supabase.from('profiles').update({role:'admin'}).eq('id', 본인id)`를 직접 호출해 거부되는지 확인 — 일반적인 사용 흐름은 아니지만 이 수정이 실제로 막는지 확인하는 가장 직접적인 방법이다.
